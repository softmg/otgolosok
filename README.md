# Отголосок

Location-aware аудиогид по Москве. Приложение предлагает короткие истории рядом с местом событий, показывает источники фактов и помогает подготовить рассказ о выбранном доме. Геопозиция обрабатывается на устройстве; выбранная точка передаётся для поиска адреса.

## Запуск

Требования: Node.js 24.20+ и pnpm 10.24+.

```bash
pnpm install
pnpm dev
```

Для проверки геолокации и PWA API по HTTPS:

```bash
pnpm dev:https
```

Детерминированная полевая проверка без запроса геолокации:

```text
http://localhost:3000/?replay=clean
http://localhost:3000/?replay=walk
http://localhost:3000/?replay=walk&speed=12
```

После нажатия «Начать прогулку» тестовый трек подаёт фиксы геолокации. Панель
«Диагностика» в replay-режиме раскрыта автоматически. Первая запись запускается
при старте, следующие по правилу из «Как включать следующую часть».

`replay=clean` подходит к одной синтетической точке и проверяет триггер как
таковой. `replay=walk` ведёт пешехода по линии маршрута со скоростью 1,4 м/с и
проходит зоны всех остановок: это проверка переходов «По месту» до выхода на
улицу. `speed` от 1 до 20 сжимает темп; помните, что ускоренный трек обгоняет
рассказ, а срабатывание удерживается, пока играет запись.

Production-проверка офлайн-режима:

```bash
pnpm build
pnpm start
```

## Docker Compose

Нужны Docker Engine / Docker Desktop с Compose v2, доступ в интернет для загрузки
образов, npm-зависимостей и карты. Node.js и FFmpeg на хосте не требуются.
Полный стек запускается одной командой, без `.env` и без дополнительных профилей:

```bash
docker compose up -d --build
```

Открыть **http://localhost:8080**. Compose автоматически поднимает nginx со
статическим Next.js export, Node.js backend с FFmpeg и Valhalla для пеших маршрутов.
Только nginx публикует порт, по умолчанию на `127.0.0.1`. Backend и Valhalla
доступны только внутри Docker-сети; `WALK_ROUTER_URL=http://valhalla:8002/route`.
Nginx обслуживает `/create`, `/admin`, `/walk` без расширения `.html` и передаёт
`/api/` backend с Origin, Authorization и Range. API не кешируется.

### Настройка

При необходимости создайте локальный `.env` по образцу `.env.example` до запуска.
Он исключён из Git и frontend build context. AI-ключи передаются только backend
во время запуска, не через build args и не в клиент. Не публикуйте вывод
`docker compose config`: он раскрывает значения; для проверки есть
`docker compose config --quiet`.

- `HTTP_PORT` и `BIND_ADDRESS` меняют опубликованный порт и интерфейс.
- `APP_ORIGIN` должен точно совпадать с адресом в браузере, без завершающего `/`.
  При смене порта обновите и его; `localhost` и `127.0.0.1` считаются разными origin.
- `OPENAI_API_KEY` и `OPENAI_BASE_URL` (HTTPS API с Responses и audio/speech)
  включают платную генерацию. Без них сайт запускается, но генерация отключена.
- `ADMIN_TOKEN` включает редакторский доступ; используйте случайный ключ минимум
  32 байта, например результат `openssl rand -hex 32`. Без ключа доступ закрыт.
- `BETTER_AUTH_SECRET` — случайный секрет Better Auth минимум 32 символа. Он
  обязателен в production. Пользователи регистрируются и входят по email и паролю;
  почтовый сервис не требуется. Восстановление забытого пароля пока недоступно.
- `USER_DAILY_GENERATION_LIMIT` задаёт персональную суточную квоту платных
  генераций; повтор того же idempotency key и готовый общий результат её не
  расходуют. `ALLOW_LEGACY_ADMIN_TOKEN` по умолчанию выключен и нужен только
  на короткое время миграции старых редакторских скриптов.
Создайте локальный аккаунт редактора командой `make admin-create EMAIL=editor@example.com`
(прямой вызов CLI: `pnpm auth:set-editor editor@example.com`).
Для нового email команда дважды запросит пароль со скрытым вводом (10–128 символов)
и создаст аккаунт с правами редактора; предварительная регистрация на сайте не нужна.
Для существующего аккаунта введите его текущий пароль: после проверки команда
назначит роль `editor`, сохранив пароль и имя. Это защищает от выдачи прав тому,
кто заранее зарегистрировал чужой email; само владение адресом сайт не проверяет.
Затем войдите с этим email и паролем на `/login?returnTo=/admin`.

Приложение должно хотя бы раз запуститься, чтобы создать схему авторизации.
Путь к существующей базе задаётся вторым аргументом, через `AUTH_DB_PATH` или
`DATA_DIR/auth.sqlite`; по умолчанию используется `backend/data/auth.sqlite`.
Команда не создаёт пустую базу при ошибке в пути.

Для production запустите из локального checkout проекта:

```bash
make admin-create-prod EMAIL=editor@example.com
```

Команда подключается по SSH к `services@93.189.230.19` и запускает CLI внутри
production-контейнера с базой `/data/auth.sqlite`. При необходимости задайте
`VPS=пользователь@хост` и `GENERATOR_CONTAINER=имя-контейнера`.
Для локальной базы можно передать `AUTH_DB_PATH=путь/к/auth.sqlite`.
Обе Makefile-команды рассчитаны на запуск из интерактивного терминала.

Если вы уже подключены к production-серверу, команда запускается прямо из каталога
сайта, без повторного SSH-подключения:

```bash
cd /srv/sites/otgolosok.softmg.tech
make admin-create-prod EMAIL=editor@example.com
```

Деплой устанавливает туда отдельный `Makefile` из `docker/production.Makefile`.
На сервере `make admin-create` служит коротким вариантом той же команды;
Node.js и исходники приложения на хосте не требуются, используется работающий контейнер.

Замените `editor@example.com` своим email. Пароль вводите в приглашении команды;
он не выводится и не передаётся через аргументы процесса. Для автоматизации доступен
`--password-stdin`: подайте пароль через стандартный ввод из защищённого источника.
Этот режим также проверяет текущий пароль существующего аккаунта и никогда его не меняет.
При работе с production используйте живую `/data/auth.sqlite` внутри контейнера,
не заменяйте её локальной копией. Создание аккаунта и пароля выполняется одной транзакцией.
- `MAX_DAILY_JOBS`, `STORY_MODEL`, `WRITER_MODEL` настраивают генератор. Поиск и автор возвращают обычный текст; машинная структура остаётся только на этапах извлечения доказательств и редакторской проверки.
- Один содержательный источник может быть достаточен, включая Википедию. Адрес публикуется только как отдельный подтверждённый факт, а название, категория и адрес сами по себе не считаются материалом для истории. PDF загружаются с отдельным лимитом 25 МиБ, антибот-заглушки и пустые JavaScript-страницы получают отдельные причины отказа. Короткая подтверждённая справка на 20–100 слов сохраняется без автоматической озвучки.
- `AIROUTER_LOGS_TOKEN` включает отправку ошибок backend в Airouter; `AIROUTER_LOGS_ENDPOINT`
  по умолчанию `https://airouter.softmg.tech`. Оба параметра передаются только backend
  при запуске Compose. После изменения `.env` пересоздайте контейнер backend командой
  `docker compose up -d --build backend`. Без токена отправка логов отключена.
- `YANDEX_TTS_API_KEY` включает Яндекс SpeechKit в выборе сервиса озвучивания
  в `/admin`. Нужен API-ключ сервисного аккаунта с ролью `ai.speechkit-tts.user`
  и разрешением ключа на синтез речи. Ключ передаётся только backend;
  идентификатор каталога для этого способа авторизации не нужен
  ([документация Яндекса](https://aistudio.yandex.ru/en/docs/speechkit/concepts/auth)).
  `YANDEX_TTS_VOICE` задаёт начальный выбор голоса, по умолчанию `marina`.
  Генерация и проверка текста по-прежнему требуют настройки OpenAI.

Чтобы озвучить редакторский текст через Яндекс, сохраните его в `/admin`,
выберите «Яндекс SpeechKit» в поле «Сервис озвучивания» и нужный голос, подтвердите проверку
и нажмите «Утвердить и озвучить». Без ключа вариант Яндекса недоступен.
Список голосов зависит от сервиса: русские голоса
[Яндекса](https://aistudio.yandex.ru/ru/docs/speechkit/tts/voices) и встроенные голоса
[OpenAI](https://developers.openai.com/api/docs/guides/text-to-speech).
Сервис и голос сохраняются при утверждении задания и используются при повторной
попытке озвучивания, даже если голос по умолчанию на сервере изменится.
При смене сервиса выбирается его голос по умолчанию. Сохранение редакторского
текста сохраняет текущий выбор в форме; обновление страницы до утверждения
сбрасывает его. Старые задания без выбора используют прежние настройки.
Интеграция использует
[SpeechKit REST API v3](https://aistudio.yandex.ru/en/docs/speechkit/tts/api/tts-v3-rest)
с автоматическим делением на фразы и запросами до 5 000 символов. Готовая
запись проходит обычную обработку MP3 и доступна для офлайна.

Для внешнего доступа используйте HTTPS reverse proxy перед nginx и задайте
`APP_ORIGIN=https://ваш-домен`. На удалённых устройствах HTTPS нужен для GPS/PWA.
Не открывайте backend или Valhalla наружу. Если reverse proxy на хосте, оставьте
loopback bind; `BIND_ADDRESS=0.0.0.0` открывает HTTP на всех интерфейсах и требует
осознанной настройки firewall. После изменения `.env` повторите `docker compose up -d`.

## Универсальные прогулки

Раздел `/walk` объединяет создание, локальную библиотеку, аккаунтные прогулки и
общие ссылки в одном проигрывателе. Локальные черновики мигрируются из старого
ключа без удаления исходной записи; сохранение в аккаунт использует revision и
идемпотентный ключ, а публикация работает через `/api/story-walks/shared/:token`.
Готовую прогулку можно сохранить без сети: комплект ограничен 60 МиБ и
проверяется по SHA-256. Подробности безопасного `WalkView`, повторов запросов и
разделения приватного кеша описаны в [`docs/agents/walks.md`](docs/agents/walks.md).

### Первый Запуск

Valhalla использует поддерживаемый upstream-образ
[`ghcr.io/valhalla/valhalla-scripted:latest`](https://github.com/valhalla/valhalla/blob/master/docker/README.md):
прежний `nilsnolde/docker-valhalla` архивирован и направляет туда.
Тег `latest` изменяемый; для воспроизводимого production-деплоя закрепите проверенный
digest образа. По умолчанию автоматически скачивается
[Moscow.osm.pbf от BBBike](https://download.bbbike.org/osm/bbbike/Moscow/Moscow.osm.pbf)
(около 81 MiB на момент проверки), затем строятся routing tiles с поддержкой
`pedestrian`. Покрытие ограничено этим extract, не всей Россией.

Выделите Docker несколько GiB RAM и несколько GiB свободного диска с запасом:
распакованные графы и временные файлы значительно больше PBF. Первый запуск может
занять минуты или значительно дольше на слабом хосте; для больших extract это
могут быть часы. `VALHALLA_THREADS=2` ограничивает параллелизм сборки и сервиса.
Сайт не ждёт построения графа: backend зависит от запуска контейнера, а не его
готовности. До готовности Valhalla запросы построения маршрута могут возвращать
ошибки; повторите их после статуса `healthy`. Готовность проверяется через
документированный `/status`, начало сборки допускается в течение часа до
отметки `unhealthy`; эта отметка сама по себе не останавливает сборку.

```bash
docker compose ps
docker compose logs -f --tail=100 valhalla
docker compose exec valhalla curl --fail http://127.0.0.1:8002/status
curl --fail http://localhost:8080/api/story-service
```

`use_tiles_ignore_pbf=True` переиспользует сохранённый tar графа при следующих
стартах. `VALHALLA_TILE_URL` можно изменить до первой сборки; с готовым томом одна
смена URL не обновит карту. Обновление PBF/принудительную пересборку выполняйте
отдельно по upstream-инструкции после резервного копирования. Автоподбор остановок
использует локальный каталог зданий Москвы; обновляйте его вместе с картой по
инструкции в `content/walk-builder.md`. Геокодер и AI остаются внешними сервисами.
Overpass используется только при явном включении внешнего подбора остановок.

### Данные И Остановка

Именованные тома `backend_data` (`/data`, принадлежит `node`) и `valhalla_data`
(`/custom_files`) сохраняют SQLite, созданные аудиофайлы и routing tiles.
Обычные пересборки и остановка не удаляют их:

```bash
docker compose down
```

**Не добавляйте `-v`**: это удалит оба тома вместе с историями и графом.
Для файлового backup остановите backend (`docker compose stop backend`) и
скопируйте весь его том, включая SQLite WAL и аудио; после копирования запустите
`docker compose start backend`. Valhalla-том резервируйте вне сборки, лучше с
остановленным сервисом. Храните резервные копии отдельно от Docker-хоста.
Копирование только живого `jobs.sqlite` не является корректным backup.
Удаление аккаунта сразу удаляет профиль и личные данные из live-БД после кода
из email, но не стирает уже сделанные резервные копии. Срок хранения backup
задаёт оператор. После восстановления старого snapshot повторите удаление
аккаунта либо удалите восстановленные строки до возврата сервиса пользователям.

Эквивалентные команды Make: `make docker-up`, `make docker-down`,
`make docker-logs`, `make docker-ps`, `make docker-config`.

### База генератора на рабочей машине

`jobs.sqlite` на проде пишется в режиме WAL, и журнал рядом с ним регулярно
больше самого файла. Копировать один `jobs.sqlite` нельзя: потеряется бо́льшая
часть свежих заданий. Все команды ниже снимают согласованный `VACUUM INTO`.

```bash
make db-dump      # снять с прода в backend/data/prod-dump, нужен доступ по SSH
make db-import    # поставить выгрузку в backend/data, сохранив прежнюю базу
make db-info      # что лежит в локальной базе
make db-restore   # вернуть последнюю сохранённую копию
```

Передать коллеге без доступа к серверу:

```bash
make db-dump && make db-pack
# получателю: tar -xzf otgolosok-prod-db-*.tar.gz -C backend/data && make db-import
```

Переменные: `VPS`, `REMOTE_DIR`, `GENERATOR_CONTAINER`, `DUMP_DIR`, `DATA_DIR`,
`ARCHIVE`, `BACKUP`. По умолчанию выгрузка, архив и резервные копии лежат внутри
`backend/data/`, который исключён из Git: в них production-данные, передавайте
их по закрытому каналу.

`db-import` сохраняет прежнюю базу в `backend/data/backup-local-<дата>` и
удаляет `jobs.sqlite-wal` и `-shm`: журнал принадлежит конкретному файлу базы,
и рядом с чужим `jobs.sqlite` он не нужен. `db-restore BACKUP=<каталог>`
выбирает копию, если их несколько.

`backend/server.mjs` не читает `.env` сам. Без `OPENAI_API_KEY` и
`OPENAI_BASE_URL` в окружении worker не стартует, и импортированные данные
остаются нетронутыми:

```bash
pnpm build && pnpm generator:dev   # http://127.0.0.1:4175
```

## Структура

- `src/app` — App Router, метаданные и PWA manifest.
- `src/features/tour` — клиентский сценарий прогулки и доменные типы.
- `src/lib/geo` — чистый геотриггер с гистерезисом и тестами.
- `src/lib/position` — источники позиции браузера и детерминированного replay.
- `src/lib/audio` — воспроизведение на единственном audio-элементе и тестовый сигнал.
- `public/data/routes` — статические данные маршрутов и POI.
- `public/audio` — четыре записи прогулки и тестовый сигнал.
- `scripts/generate-walk-audio.py` — разовая генерация MP3 через Speech API.
- `content` — редакторское досье первой карточки и план генерации за 5–10 минут.
- `public/sw.js` — Service Worker для офлайн-запуска, данных и аудио.
- `scripts/build-service-worker.mjs` — формирует список файлов и версию кэша после статического экспорта.
- `scripts/prod-db.mjs` — выгрузка базы генератора с прода, импорт и откат на рабочей машине.
- `scripts/check-stress.mjs` — проверка разметки ударений для SpeechKit перед синтезом.

После первого открытия production-сборки дождитесь сообщения «Офлайн-копия готова».
Теперь приложение можно перезагрузить без сети: сохраняются HTML, JavaScript, CSS,
шрифты, иконки, маршрутные данные и локальные аудиофайлы. Новый Service Worker
по умолчанию ждёт закрытия вкладок, чтобы обновление не прерывало прогулку.
На главной есть «Проверить обновление» и уведомление о готовой новой версии.
Кнопка открывает `/update.html`, активирует полностью загруженную версию и
переходит к началу актуальной прогулки. Эта ссылка работает и для старых
версий без кнопки. Во время прогулки кнопка обновления скрыта.

Страница обновления и её JS/CSS не входят в офлайн-кэш и отдаются с `no-store`.
При ошибке сети или ожидании дольше 25 секунд доступен повтор; сохранённая
версия не удаляется. Другие вкладки не перезагружаются принудительно: при
активации с открытыми окнами их старые ресурсы сохраняются. Очистка старых
кэшей выполняется при последующей активации без открытых окон.

## Зафиксированные ограничения MVP

- Геопозиция обрабатывается в браузере. Карта запрашивает сторонние тайлы; явно выбранная точка или введённый адрес передаются геокодеру через API сайта.
- Геолокация запускается сразу после нажатия, независимо от готовности звука.
- Ожидание активации звука ограничено 3 секундами, запуска аудио — 10 секундами.
  Если браузер не отвечает, звук можно повторно включить кнопкой; прогулка остаётся доступной.
- Экран удерживается активным через Wake Lock, если API доступен.
- Wake Lock повторно запрашивается после возврата во вкладку и освобождается при завершении прогулки.
- Первая прогулка включает базовые текст и MP3; кабинет редактора может публиковать новые версии глав. Новые истории готовит отдельный Node.js сервис.
- Текущая прогулка: 2-й Кожевнический переулок, 12с10 → Дербеневская
  набережная, 7с22; примерно 650 м, 8 минут ходьбы, план 15 минут с чтением.
  Четыре последовательные части используют три заметки и историю фабрики.
  Для мануфактуры Цинделя подготовлен текст
  на 183 слова, восемь фактов с подтверждениями и пять источников. В рассказ
  включён эпизод с Варварой Степановой и её платьем на фотографии Родченко. Читать историю
  можно без геолокации и офлайн; в режиме прогулки показывается текущая часть.
  Доступны «Назад» и «Дальше», переходы между сюжетами и источники каждой части.
  Плеер поддерживает паузу, продолжение, перемотку на 15 секунд, шкалу времени
  и скорость рассказа от 0,8× до 1,5×. Название части, кнопки и перемотка
  выведены на экран блокировки и кнопки гарнитуры через Media Session, поэтому
  телефон может оставаться в кармане. На экране прогулки есть карта с линией
  пути, отметками частей и вашим положением; её можно свернуть.
  При выходе или перезагрузке сохраняется часть и позиция в записи; на главной
  доступны «Продолжить прогулку» и «Начать сначала». «Закончить маршрут»
  после финальной части очищает сохранённую позицию.
- Утверждения привязаны к источникам, абзацы к фактам. Редакторские решения и
  исключённые сведения записаны в [досье](content/first-card.md).
- В разделе «По дороге» доступны три заметки на 45–55 секунд чтения:
  Кожевнические переулки и имя Ивановская, старые названия Дербеневской,
  дома для служащих и рабочих фабрики (10 и 14, корпуса 2 и 5).
  Во вкладке «Прогулка» они раскрываются отдельно; во время прогулки встроены в последовательность,
  включая короткие переходы. Тексты, карта и четыре записи доступны офлайн.
  Синтетическая озвучка включается при старте и переходе к следующей части.
  Проверенные сведения и ограничения: [досье заметок](content/route-notes.md).
- Точка остановки и обзор на месте ещё не проверены.
- «Как включать следующую часть» на экране прогулки выбирает одно из трёх:
  «По кнопке» (по умолчанию), «По месту» и «Подряд». Выбор сохраняется в
  localStorage этого браузера. По умолчанию оставлена кнопка, пока подходы к
  остановкам не проверены на местности; `?replay=walk` проверяет «По месту»
  детерминированно.
- В режиме «По месту» триггер следит за остановкой той части, которая должна
  зазвучать следующей, и удерживает срабатывание, пока играет текущая запись.
  Если дом стоит в стороне от маршрута, точка срабатывания задаётся отдельно
  полем `trigger_location`: у «Жизни после смены» дом на Дербеневской в 63 м от
  линии, дальше зоны входа в 35 м, поэтому часть включается с улицы.
  Переключение части останавливает предыдущую запись и запускает выбранную.
  Геолокация показывает расстояние до следующей части по прямой; это не
  оставшаяся длина пешего пути.
- Прогресс хранится в localStorage этого браузера, без GPS-координат.
  Он относится к конкретной версии MP3: замена записи сбрасывает её старое
  время. При запрете browser storage прослушивание остаётся доступным,
  но восстановить место после перезагрузки нельзя.
- Схема маршрута во вкладке «Прогулка» построена из геометрии OpenStreetMap; SVG генерируется перед сборкой,
  линия пешего пути взята из Valhalla. Карта не загружает сторонние тайлы и
  не отправляет геопозицию. [Данные карты](content/map.md),
  [сценарий короткой прогулки](content/short-walk.md).
- На `/create` доступна подготовка истории по введённому московскому адресу:
  источники, проверка фактов и рассказа, озвучка, сохранение для офлайна.
  Задание выполняет отдельный Node.js сервис; закрытие вкладки его не отменяет.
  [Запуск и ограничения генератора](content/generator.md),
  [целевые сроки и редакционные правила](content/generation-plan.md).
- Стартовый экран «Что вокруг вас» показывает интерактивную карту OpenStreetMap,
  готовые истории и задания, созданные с карты на этом устройстве. Поиск адреса
  и генерация запускаются по отдельному нажатию. [Устройство карты](content/around-map.md).
- Production-клиент экспортируется в `out/`; сервер генерации отдельно
  обслуживает `/api/story-*`, включая определение адреса.

## Редакционный кабинет

На `/admin` доступны таблицы «Адреса», «Прогулки» и «OSM-партии». Вход выполняется
через аккаунт с ролью редактора. Старый `ADMIN_TOKEN` используется только при
явном `ALLOW_LEGACY_ADMIN_TOKEN=true`.

- Адреса можно искать по названию или ID, фильтровать по состоянию и отмечать
  нерелевантными. Такие записи скрыты из активной очереди; фильтр
  «Нерелевантные» позволяет найти их и вернуть. Отметка управляет редакционной
  очередью, уже запущенная подготовка продолжает работу.
- Для задания, прерванного до готовности текста, доступно «Продолжить
  подготовку» с выбором сервиса и голоса. Готовую историю можно переозвучить
  без повторного поиска фактов; предыдущая запись остаётся доступной до успеха.
- Во вкладке прогулок показаны встроенные маршруты и их главы. Переход,
  абзацы и финальную подсказку можно отредактировать, сохранить и переозвучить
  выбранным голосом. Сохранение черновика не меняет публичную прогулку:
  текст и запись публикуются вместе после успешного синтеза.
- Личные маршруты конструктора пока сохраняются только в браузере автора
  и в серверной таблице прогулок не появляются.

Редактура глав хранится в таблице `walk_chapters` существующей SQLite.
Генерация адресов и глав использует один worker и общие лимиты. Публичный
`GET /api/story-walks/:routeId` возвращает опубликованную версию; открытая
сессия прослушивания сохраняет свой текст и аудио до завершения.
Новая версия прогулки сохраняется для офлайна вместе со всеми её записями;
при недоступности сервиса используется последняя полная копия или базовый маршрут.
Backend содержит автоматически созданный каталог `backend/builtin-routes.mjs`
для самостоятельного Docker-образа. После изменения исходных маршрутов
запустите `node scripts/build-walk-catalog.mjs` (также входит в `pnpm build`).
Проверка соответствия: `node scripts/build-walk-catalog.mjs --check`.

## Проверки

## Локальный TTS-воркер

Backend может выдавать готовые тексты внешнему компьютеру и принимать завершённое
аудио. Домашний компьютер делает только исходящие HTTPS-запросы; открывать на нём
порт не требуется. На сервере задайте секрет lease. Токены отдельных воркеров
выпускаются и отзываются в `/admin?section=content`; статический
`WORKER_API_TOKEN` оставлен для совместимости. Секреты должны быть независимыми:

```text
WORKER_API_TOKEN=<случайный токен не короче 32 байт>
WORKER_LEASE_SECRET=<другой случайный секрет не короче 32 байт>
```

При `LOCAL_TTS_TRANSPORT=worker` backend не запустится в production (или при заданном
`WORKER_API_TOKEN`), если `WORKER_LEASE_SECRET` пуст или короче 32 символов: токены аренды
подписываются этим секретом, и известное значение по умолчанию позволило бы их подделать.
В локальной разработке без секрета генерируется случайный секрет на время жизни процесса.

После перезапуска backend поставьте утверждённый адресный рассказ на локальную
озвучку через редакторский API:

```text
POST /api/story-admin/jobs/:id/external-audio
Authorization: Bearer <ADMIN_TOKEN>
Origin: <APP_ORIGIN>
Content-Type: application/json

{"revision":12,"profileId":"silero-ru-v1"}
```

Настройка и запуск компьютера с Silero описаны в отдельном репозитории
[`just-tts`](https://github.com/NickZaitsev/just-tts). Воркер забирает одно задание,
продлевает lease во время синтеза и загружает WAV. Сервер проверяет checksum и
длительность, нормализует громкость, сохраняет MP3 в постоянный `/data/audio` и
только после этого публикует запись. Для проверки протокола без модели есть
`just-tts --env-file .env worker --once`.

Сервер до постановки задания фиксирует нормализованный `spokenText`, его checksum,
версию нормализатора и контракт TTS-профиля. При правке утверждённого текста старый
lease отменяется, а новая версия текста и новое аудио получают отдельные immutable
записи. Одновременно сервер обрабатывает не более двух входящих аудиофайлов.

Каталог кандидатов из OSM PBF собирается командой:

```text
python scripts/import-osm-attractions.py Moscow.osm.pbf --output backend/data/osm-attractions.json \
  --source-url https://download.geofabrik.de/russia/central-fed-district-latest.osm.pbf \
  --coverage moscow-admin --boundary-file moscow-boundary.geojson --boundary-relation-id 102269
node scripts/load-osm-catalog.mjs backend/data/osm-attractions.json --complete
```

Для скрипта импорта нужен `osmium==4.3.1` в отдельном build-окружении. Выходной
каталог содержит provenance, checksum снимка и ODbL attribution. Полный импорт
требует extract, содержащий relation Москвы `102269`, и проверенную границу Москвы.
Передайте проверенный GeoJSON и зафиксируйте его checksum:
`--coverage moscow-admin --boundary-file moscow-boundary.geojson`; импорт обрежет
каталог по Polygon/MultiPolygon и отметит покрытие как административное. Флаг
`node scripts/load-osm-catalog.mjs ... --complete` принимается только для такого
каталога с checksum границы; лишь полный импорт архивирует исчезнувшие объекты.
После загрузки каталог виден в разделе `/admin?section=content`: там можно создать
партию до 5 000 объектов, поставить её на паузу, продолжить или отменить. Серверный
воркер готовит тексты последовательно и сохраняет промежуточные стадии. Режим
`text-and-audio` ставит текст в очередь TTS после редакторского утверждения.
При `CONTENT_AUTO_APPROVE=true` текст, который прошёл автоматическую проверку фактов и модельную редактуру без замечаний,
сразу публикуется и ставится в очередь TTS выбранного профиля. Состояния `review_required`, `insufficient_evidence` и `failed`
автоматически не публикуются. По умолчанию флаг выключен.
В том же экране доступны состав партии, повтор отдельной ошибки, редактура текста,
повторная озвучка, одноразовая выдача токена, отзыв ключа и последний heartbeat.

Для эксплуатационного запуска сначала создайте разнообразный пилот. Скрипт выбирает
разные OSM-категории и не менее четверти объектов без почтового адреса, если они есть:

```bash
node scripts/create-osm-batch.mjs --pilot --limit 50
```

Новая партия по умолчанию создаётся на паузе. После проверки настроек провайдера
возобновите её в админке; `--start` запускает обработку сразу.

После проверки фактов редактором и прослушивания Silero создавайте следующие партии.
`--next` пропускает места, для которых текущее содержимое уже поставлено в очередь,
поэтому последовательные вызовы охватывают весь снимок без повторов:

```bash
node scripts/create-osm-batch.mjs --next --limit 5000
```

Перед массовым запуском зафиксируйте checksum и лицензию модели, голос, CPU/GPU и
память целевой машины. Для пилота запишите расход токенов из админской метрики,
время синтеза и память процесса; вручную проверьте факты, имена, даты, адреса,
ударения и отсутствие обрывов в каждом принятом результате. Массовые партии можно
создать заранее на паузе, но не запускайте их, пока пилот не прошёл эту проверку.

Реальный пилот 16 сентября 2026 года обработал 50 разнообразных объектов из полного
снимка: 7 текстов прошли автоматическую и ручную редактуру и были озвучены Silero
голосом `xenia`, 43 объекта завершились честными `insufficient_evidence`,
`review_required` или `failed`. Девять MP3, включая два результата начала массовой партии,
прошли серверную нормализацию, checksum, `HEAD` и byte-range проверку; суммарная длительность — 327,94 с, объём — 2 630 037
байт. Docker/nginx smoke также передал бинарный WAV через `/api/worker/v1/.../result`
до backend и получил ожидаемый ответ lease-проверки. Полный снимок из 6 107 объектов
распределён между пилотом и двумя массовыми
партиями (5 000 и 1 057); массовые партии оставлены на паузе после низкого выхода
пилота. Их можно запускать после улучшения источников и редакционного профиля.

Озвучка уже включена в репозиторий и обычную сборку. Для её регенерации нужны
Python 3 с `ru-normalizr==0.3.0` (`python3 -m pip install ru-normalizr==0.3.0`), `ffmpeg`, `ffprobe` и переменные окружения `OPENAI_API_KEY`,
`OPENAI_BASE_URL` (совместимый endpoint с `/audio/speech`). Ключи не попадают
в клиент. Запуск: `python3 scripts/generate-walk-audio.py`.
Это отдельный платный API-вызов, `pnpm build` синтез речи не запускает.
Происхождение и проверки записей: [озвучка](content/narration.md).

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

### Ударения в разметке SpeechKit

Ударение `+` выключает у слова словарное произношение: SpeechKit читает его
по буквенным правилам. Для слов, которые пишутся не так, как звучат, это ломает
озвучку — `Сегодня` синтезируется как «севодня», а `Сег+одня` уже с буквенным «г».
Ударение в таких словах и так однозначное, поэтому метку безопасно снять.

`backend/stress-safety.mjs` находит такие метки, `scripts/check-stress.mjs` —
обёртка для ручной вычитки глав и для CI:

```bash
node scripts/check-stress.mjs chapter.txt          # отчёт, код возврата 1 при находках
node scripts/check-stress.mjs --fix chapter.txt    # исправленная разметка в stdout
node scripts/check-stress.mjs --fix --high in.txt  # снять только метки уровня high
```

Уровень `high` — лексические и морфологические сдвиги (`-ого/-его`, `что`,
`конечно`), где буквенные правила синтезатора заведомо не помогут. Уровень
`medium` — регулярные упрощения групп (`-тся`, `стн`, `сч`, `гк`), которые
движок может отработать сам; они снимаются по умолчанию, но это можно отключить.

Сам пайплайн генерации ударения не расставляет. Если добавлять автоматическую
расстановку (например, `ruaccent`), чекер обязателен: библиотека помечает в том
числе `Сег+одня`, `ег+о` и `пр+ошлого`.
