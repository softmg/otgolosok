## Приоритетные замечания

### 1. P1: один idempotency key позволяет обходить персональную квоту

Места: `backend/server.mjs:397–404`, `backend/account-store.mjs:68–70`.

`reserveGeneration()` считает повтор ключа уже оплаченным запросом, однако обработчик продолжает создавать задание по новому адресу. `attachRequest()` возвращает прежний job ID, но обработчик игнорирует возвращаемое значение и отдаёт новое задание. Ключ не связан с параметрами операции.

Воспроизведено локальными HTTP-запросами с настоящими SQLite store и account store, подставной пользовательской сессией и выключенными воркерами: семь разных адресов с одним `idempotencyKey` дали семь ответов 200 и семь разных job ID. В персональной квоте записана одна единица, в истории аккаунта — одно задание. Для изоляции персонального лимита глобальные `maxDaily` и `maxActive` в стенде увеличены до 20. Глобальные ограничения это не отменяет, но позволяет одному аккаунту занимать доступную общую ёмкость, обходя свой лимит.

Исправление: до создания задания сопоставлять ключ с пользователем, типом операции и нормализованными параметрами. Повтор того же запроса возвращает прежний результат; тот же ключ с другими параметрами даёт 409 без создания задания и изменения квоты. Учесть восстановление после сбоя между записями в `auth.sqlite` и `jobs.sqlite`; одна транзакция account store не делает две базы атомарными. Аналогичный контракт проверить у исследования прогулок.

### 2. P1: отклонённая загрузка может удалить ранее опубликованное аудио

Места: `backend/server.mjs:145–149`, `backend/audio-ingest.mjs:36–39`.

`ingestAudio()` кладёт MP3 сразу в общий путь `<sha256>.mp3`. Если checksum входной загрузки не совпал или публикация завершилась ошибкой, обработчик удаляет этот путь. Такой файл мог существовать до загрузки и использоваться другими историями. Отсутствие receipt у текущего задания ничего не говорит об остальных ссылках на файл.

Воспроизведено через HTTP с временным каталогом и подставным ingest-адаптером: заранее существовавший файл исчез после ответа 422 `AUDIO_CHECKSUM`. Тест подтверждает поведение обработчика; совпадение результата реального FFmpeg для двух загрузок отдельно не воспроизводилось.

Исправление: проверять checksum загрузки до помещения результата в общее хранилище, явно разделить временный файл и опубликованный артефакт. Обработчик ошибки удаляет только собственные временные файлы. Уборка общих файлов должна учитывать все ссылки и гонки публикации; безопаснее оставить неподтверждённый общий артефакт до отдельной уборки, чем удалить используемую запись. Проверить также истечение lease во время обработки.

### 3. P2: Windows-сборка создаёт неполный офлайн-кеш

Место: `scripts/build-service-worker.mjs:5–8`.

Рекурсивный `readdir()` в Windows возвращает вложенные пути с обратными слешами. Фильтр ожидает `/`, поэтому вложенные JS, CSS, шрифты, карты и MP3 не попадают в manifest.

Воспроизведено обычным `pnpm build`: сборка успешна, но выводит `Service Worker: 7 files`. В `out/sw.js` нет ни одного JS или MP3 в `assets`. Сохранённый HTML без скриптов не обеспечивает работу приложения после отключения сети. Linux-сборка в Docker использует другие разделители; найденная ошибка относится к сборке на Windows.

Исправление: нормализовать относительные пути до фильтрации, хеширования и создания URL. Проверять сгенерированный manifest, а не только поведение service worker с вручную заданным набором assets. В существующих тестах `src/lib/offline/service-worker.test.ts` manifest подставляется вручную.

### 4. P2: returnTo допускает перенаправление на внешний сайт после входа

Место: `src/features/auth/login.tsx:10`.

Проверки `startsWith('/')` и `!startsWith('//')` пропускают строку, начинающуюся с `/` и обратного слеша. WHATWG URL для HTTP(S) трактует обратный слеш как разделитель. Например, `/login?returnTo=%2F%5Cexample.test` после входа направляет пользователя на внешний origin.

Воспроизведён разбор URL: строка проходит текущую проверку, а `new URL(target, 'https://otgolosok.test').origin` равен `https://example.test`. Полный вход через браузер с таким URL не запускался. Это открытое перенаправление, а не доказанная передача session cookie внешнему сайту.

Исправление: разбирать URL относительно текущего origin и разрешать переход только при совпадении origin и допустимой схеме. При ошибке использовать `/account`. Возвращать проверенные pathname, search и hash, сохранив обычные внутренние ссылки.

### 5. P2: любое изменение localStorage в другой вкладке перенаправляет личный кабинет

Место: `src/features/account/account.tsx:15`.

Обработчик `storage` без проверки `event.key` вызывает `signedOut()`. Достаточно изменить черновик в другой вкладке конструктора (`src/features/walk-builder/walk-builder.tsx:68`) или записать прогресс аудио, чтобы кабинет перешёл на страницу входа. Это не отзыв сессии: действующая сессия может сразу вернуть пользователя в кабинет, но введённое несохранённое имя будет потеряно.

Подтверждено чтением обработчика и мест записи localStorage; многовкладочный браузерный сценарий не запускался.

Исправление: реагировать только на предусмотренный ключ события выхода и сообщение `signed-out` в BroadcastChannel. Обычные изменения черновиков, прогресса и других ключей должны игнорироваться.

### 6. P2: личный кабинет скрывает записи после первой страницы

Места: `src/features/account/account.tsx:15`, `backend/server.mjs:84–96`, `backend/account-store.mjs:60–72`.

Сервер поддерживает курсоры, а HTTP API по умолчанию возвращает 20 элементов. Клиент однократно загружает прогулки, запросы и избранное и не сохраняет `nextCursor`. Элементы после первых двадцати недоступны из списков кабинета, хотя остаются в базе.

Подтверждено сопоставлением API и клиента. Исправление: независимая загрузка следующих страниц для трёх списков с сохранением уже показанных данных при сетевой ошибке и защитой от дублирования элементов.

## Дополнительные улучшения

- В кабинете все запросы ведут на `/create?job=…`, включая `walk_research`, тогда как `GET /api/story-jobs/:id` намеренно исключает исследования прогулок. Нужен отдельный переход с восстановлением исследования в конструкторе. Это самостоятельный дефект интеграции; способ открытия стоит определить при реализации.
- `saveToAccount()` в `src/features/walk-builder/walk-builder.tsx:224` создаёт новый ключ при каждом повторе POST. При потерянном ответе повтор сохранения может создать дубликат прогулки. Сохранять ключ одного намерения до получения однозначного результата.
- Сначала покрыть реальные стыки тестами: генерация с account store, отклонённая загрузка при существующем MP3, результат сборки SW, вход и кабинет в нескольких вкладках. Текущие HTTP-тесты часто подставляют account store или авторизацию; отдельные тесты store не заменяют проверки их совместной работы.
- После исправления поведения разнести маршруты `backend/server.mjs` по предметным модулям и форматировать длинные обработчики. `src/features/tour/tour-experience.tsx` содержит 837 строк и несколько обязанностей; выделять управление воспроизведением, геопозицией и офлайн-состоянием постепенно, с сохранением тестов.
- `pnpm typecheck` охватывает TypeScript, но не проверяет типы backend `.mjs`: в `tsconfig.json` нет `checkJs`, а include перечисляет TS-файлы. Вводить JSDoc/проверку JS постепенно на границах API, без массовой миграции ради самой миграции.
- Python-тесты импортера существуют, но не входят в `pnpm test`. Добавить их в документированный общий запуск проверок. В репозитории не найдено настройки CI или браузерного тестового запуска; автоматизацию предложить отдельно, с учётом выбранного хостинга репозитория.
