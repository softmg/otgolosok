# Резервная копия генератора через снимки SQLite

2 октября 2026 года выкладка генератора откатилась на резервном копировании:
`tar: generator-data: file changed as we read it`. Backend был остановлен, но
сторонние SSH-сессии открыли `auth.sqlite`. Появился `auth.sqlite-wal`, каталог
изменился, `tar` вернул код 1, и скрипт посчитал это ошибкой. Время сессий в
`journalctl` совпало со временем изменения файлов.

Бэкап делает `deploy-scripts/otgolosok-generator-backup.sh` из проекта
services. На сервер он копируется как `generator-backup.sh`.

## Два этапа

1. `prepare BACKUP_DIR IMAGE` выполняется при остановленном backend:
   снимает базы, создаёт несжатый `generator.tar`, проверяет структуру и
   наличие обязательных файлов. `generator.members` содержит список
   обязательных файлов для последующей проверки. Снимки SQLite удаляются
   после включения в архив.
2. После запуска нового backend, получения `healthy` и удаления
   `maintenance/active` команда `finalize BACKUP_DIR` сжимает готовый tar,
   читает сжатый архив до конца и проверяет обязательные файлы.
   Живые данные на этом этапе не читаются.
3. Только после успешной проверки появляется `generator.tar.gz`,
   а tar и список обязательных файлов удаляются. Только такой архив
   участвует в ротации трёх последних полных резервных копий.

Совместимый вызов `BACKUP_DIR IMAGE` выполняет оба этапа подряд;
он подходит для ручного бэкапа уже остановленного сервиса.

Живые базы `generator-data/*.sqlite` верхнего уровня архивируются снимками
`VACUUM INTO`, затем проходят `PRAGMA quick_check`. Файлы `-wal`/`-shm`
не включаются, копии в `ops-backups/` и `maintenance-backups/` остаются
обычными файлами. Структура итогового архива и способ восстановления прежние.

Код 1 от `tar` (каталог или медиа изменились во время чтения) — предупреждение,
коды от 2 — ошибка. При неудаче подготовки временные файлы удаляются,
а деплой возвращает прежние образ, Compose и каталог исходников backend.
Обычное прерывание HUP/INT/TERM во время обслуживания также запускает откат.

## Сбой сжатия

Если `finalize` завершился с ошибкой, новый backend продолжает работать,
режим обслуживания остаётся выключенным, команда деплоя возвращает ошибку.
Проверенный несжатый архив и `generator.members` сохраняются для повтора;
ротация не удаляет такие подготовленные копии даже через час.

Повторять упаковку нужно из каталога сайта с той же серверной блокировкой:

```bash
flock -n .deploy.lock bash generator-backup.sh finalize backups/generator-<время>
```

Незавершённую копию нужно довести до полного архива либо удалить вручную
после проверки других резервных копий: она занимает место до завершения
работы оператора. Не считать `generator.tar` полным сжатым бэкапом.

## Размер архива и простой

Архив включает весь `generator-data`, в том числе вложенные копии данных.
При размере несжатого архива около 8,4 ГБ однопоточный `gzip` работает
дольше семи минут. Теперь это время не входит в режим обслуживания:
backend остановлен только для фиксации и проверки несжатой копии,
переключения образа и ожидания готовности. Копирование данных по-прежнему
занимает время, поэтому нулевой простой не гарантируется.

Весь серверный этап, включая сжатие и ротацию, удерживает `.deploy.lock`;
второй деплой отклоняется до изменений общих файлов. Загрузка исходников
происходит в отдельный временный каталог каждого запуска.

## Проверки

`tests/otgolosok-generator-backup.test.sh` в проекте services проверяет
снимки с WAL, вложенные копии, повреждённую базу, совместимый вызов,
раздельные этапы, отсутствие зависимости упаковки от живых файлов,
ошибку сжатия и повторную упаковку. Тест запускается на VPS в отдельном
временном каталоге с настоящим образом генератора.

`tests/otgolosok-generator-deploy.test.sh` в том же проекте проверяет
порядок запуска и сжатия, отказ при занятых очередях, откат при ошибке
готовности, сохранение обслуживания сайта при сбое сжатия, прерывание
и отказ параллельной выкладке. Жизненный цикл контейнера моделируется;
снимки SQLite и архивы настоящие. Production-каталоги тесты не трогают.
