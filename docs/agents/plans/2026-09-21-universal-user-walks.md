## Контекст

«От Кожевников к Цинделю» сейчас занимает особое место в приложении: JSON импортируется непосредственно главной страницей, экран прогулки содержит фиксированные подписи, карту и предположения о четырёх главах. Пользовательские маршруты уже можно строить и сохранять, но они живут в другом формате и не подключены к этому проигрывателю. Замена одного JSON на массив JSON не решает проблему.

Цель — единый жизненный цикл: создать маршрут → сохранить → открыть → идти и слушать → при желании поделиться. Кожевники становятся начальной записью каталога, которую отображает тот же механизм, что и произвольную пользовательскую прогулку. Данные конкретного района могут остаться данными, но не условиями в интерфейсе или проигрывателе.

Существующие внешние зависимости сохраняются: пешеходный маршрутизатор принимает POST по настроенному `WALK_ROUTER_URL`, поиск адреса проходит через `/api/story-place`, генерация — через существующие задания. Дополнительных провайдеров, платных вызовов и новых переменных окружения этот рефактор не требует. Цена существующей генерации зависит от настроенных провайдеров и из кода не определяется. Открытие, сохранение и публикация прогулки сами по себе не должны заказывать исследования или озвучку.

## Согласованные решения

1. Любая пользовательская прогулка открывается и воспроизводится общим механизмом `TourExperience`. Кожевники — одна из прогулок, без собственного пользовательского сценария.
2. Главная остаётся картой «Рядом». В нижней навигации убрать отдельную кнопку «Создать», оставить «Рядом», «Прогулка», «Кабинет». В разделе «Прогулка» сверху разместить создание, ниже — список прогулок. С карты сохранить переход к созданию от выбранного места.
3. Собирать и локально сохранять прогулки можно без входа. Для сохранения в аккаунте и публичной ссылки нужен вход. Существующие требования авторизации и квоты платной генерации не ослаблять.
4. Прогулка личная по умолчанию. Владелец явно включает и выключает доступ по ссылке. Ссылка содержит случайный UUID/токен без имени пользователя.
5. Публичная ссылка показывает последнюю сохранённую редакцию владельца. Отдельного действия «обновить публикацию» нет; несохранённые изменения не публикуются.
6. Разрешена публикация с незавершёнными историями. Остановки сохраняют порядок и место в маршруте; незавершённая история отображается как подготовка. У остановки одна история, подготовка выполняется последовательно в рамках существующих механизмов.
7. Пользователь завершил обсуждение указанием «пиши план». Допущения реализации, которые не выдаются за отдельно подтверждённые ответы: публикация означает доступ по ссылке без включения в общий каталог; готовые части можно слушать до завершения остальных; начальная прогулка доступна всем как пример. Общий каталог чужих публикаций в эту работу не входит.
8. Сохранить ручное переключение по умолчанию, существующие режимы геотриггера/последовательного воспроизведения и восстановление прослушивания. Обновление данных не должно прерывать уже играющую запись.

### 1. Общий документ маршрута и безопасное представление

Создать `backend/walk-document.mjs` как чистый модуль без Node API, с JSDoc-типами, пригодный для использования на клиенте; экспортировать его типы через `src/features/walks/model.ts`. Использование пути `backend/` сохраняет существующий способ упаковки Docker, который копирует `backend/*.mjs`. Клиент импортирует только этот чистый модуль, без store/auth.

Определить два контракта вместо попытки сохранить внутренние задания как публичный JSON:

- `WalkDocument` версии 2: ID, название, описание, город, режим пути, старт/финиш, упорядоченные остановки со стабильными ID, фактическая геометрия и измерения либо `null`, признак проверки на местности. Каждая остановка содержит место, координаты/точку триггера, необязательные переход и подсказку, `storyRef` либо `null`. Типы ссылок: адресное задание, опубликованное OSM-место, запись контентного каталога. Старт сам по себе не требует истории: отдельная глава старта сохраняется там, где она уже была заказана; возврат замкнутого пути не дублирует главу.
- `WalkView`: документ для отображения с безопасно разрешённой историей каждой остановки, статусом, текстом/источниками/фактами и аудио либо `null`, revision документа и версией содержимого. История может быть `not_requested`, `preparing`, `text_ready`, `ready`, `failed`, `review_required`, `insufficient_evidence` или `unavailable`. Не изображать терминальную ошибку как вечную подготовку.

Сигнатуры: `validateWalkDocument(value: unknown): WalkDocument`, `migrateLegacyDraft(value: unknown, walkId: string): WalkDocument`, `validateWalkView(value: unknown): WalkView`. Ошибки имеют ограниченный код и русское публичное сообщение.

Проверять допустимые ключи, размеры текста и массивов, конечность/границы координат, уникальность ID, ссылки, совпадение порядка точек с маршрутом. Использовать действующие ограничения конструктора: 1–5 остановок сверх старта, режимы loop/open, бюджет 30/60/90 для построения; фактические 15 минут начального примера не превращать в недопустимый бюджет конструктора. Черновик без геометрии допустим, запуск требует построенного пути. Не выдавать клиентский флаг `fieldChecked` за проверку редактором.

Отдельно хранить внутреннее состояние подготовки (`research`, recovery token, `submitting`, ключи идемпотентности), не включать его в `WalkView`. В публичном DTO использовать явный список полей; не возвращать snapshot целиком, owner/email, recovery token, задания редактора или внутренние ошибки. Приватные данные не должны попадать в публичный JSON даже при намеренно присланных лишних полях.

### 2. Локальная библиотека и миграция без потери черновиков

Создать `src/features/walks/local-store.ts` и тесты. Хранить несколько документов по стабильным UUID в версионированном локальном формате, с revision для конфликтов вкладок и явными операциями создания/чтения/обновления/удаления. Для небольших документов достаточно существующего localStorage; аудио остаётся в Cache Storage. Не добавлять IndexedDB без необходимости.

Мигрировать `otgolosok:walk:v1` идемпотентно: сохранить исходную строку до успешной записи и проверки новой версии, зафиксировать соответствие старого черновика новому ID. Повторное открытие не создаёт дубликат. При повреждении, запрете storage или превышении квоты показать ошибку, сохранить данные в памяти и возможность скачать копию; не подменять черновик пустым.

Изменить `walk-builder/model.ts`, `walk-builder.tsx`, `research-panel.tsx` и `account/account.tsx`: конструктор редактирует выбранный документ, ссылки заданий сопоставляются со стабильными остановками. Перестановка точек сохраняет их ID и связанные истории, изменение координат/состава инвалидирует геометрию. Старые задания остаются в истории подготовки, но не превращаются в лишние остановки.

Разделять анонимные локальные документы и локальные данные аккаунта по user ID. При выходе прекращать запросы и скрывать/очищать приватные снимки и прогресс аккаунта; анонимные черновики сохранять. Открытие серверного ID не должно перезаписывать другой локальный документ.

Сохранение в аккаунт должно переживать потерю ответа: сохранять один ключ на операцию, повторять тот же payload с тем же ключом, подтверждать успешный ответ перед обновлением локального соответствия ID. Для PATCH сохранить проверку revision и явный конфликт без затирания чужой редакции.

### 3. Хранение, разрешение историй и публичная ссылка

Изменить `backend/account-store.mjs`, `backend/server.mjs`; создать `backend/user-walks.mjs` для разрешения представления из существующих store.

Сделать аддитивную миграцию `user_walks`: поля версии документа, `visibility` private/shared, уникальный случайный `share_token`. Не менять FK владельца и CAS по revision. Переписать INSERT с явным перечислением колонок до расширения таблицы. Старые snapshot мигрировать при чтении/сохранении; повреждённые записи не удалять, отдавать владельцу диагностируемую ошибку с возможностью выгрузить исходник. Старое API сохранения version 1 временно принимать через мигратор, чтобы обновление PWA не ломало открытые вкладки.

Новые/изменённые API:

- `GET /api/me/walks`: ограниченный пагинированный список карточек без полного snapshot; детали остаются в `GET /api/me/walks/:id`.
- `POST /api/me/walks` и `PATCH /api/me/walks/:id`: валидированный документ и внутреннее состояние владельца. Идемпотентность создания привязана к отпечатку payload; повтор с другим payload — 409. Исправить также импорт через `/api/me/import`, который использует тот же store.
- `GET /api/me/walks/:id/view`: представление для проигрывателя только владельцу.
- `PUT /api/me/walks/:id/sharing` с `{revision, enabled}`: CAS, сессия и CSRF. Первое включение создаёт токен; изменения документа сохраняют ссылку. Выключение делает её недоступной, повторное включение восстанавливает тот же токен. Повтор операции с потерянным ответом должен иметь определённый идемпотентный результат.
- `GET /api/story-walks/shared/:token`: актуальное безопасное представление без входа. Приватная/удалённая/неизвестная прогулка возвращает одинаковый 404. Списка всех пользовательских публикаций нет.
- `GET /api/story-walks`: список общедоступных начальных записей; `GET /api/story-walks/:id` сохранить совместимым для старых клиентов. Для нового формата добавить `GET /api/story-walks/:id/view`.

При разрешении `storyRef` проверять тип, доступность, связь с местом и допустимость содержимого. Владелец не может опубликовать произвольный редакторский черновик, токен или приватное исследование через ссылку. Использовать существующие опубликованные/публично доступные результаты; переход на ready определяется сервером, не присланным stage. Отсутствующая/скрытая история оставляет остановку со статусом unavailable. Для OSM использовать опубликованную версию, для каталога — действующую редакторскую публикацию, для адресных заданий — допустимые публичные данные, исключая неутверждённые тексты.

`resolveWalkView(document, {storyStore})` не делает сетевых запросов и не запускает генерацию. Ссылки разрешаются заново при чтении: завершение задания отражается без ручного пересохранения прогулки. Согласованность двух баз обеспечивается версионированным документом и проверками отсутствующих ссылок, а не обещанием общей транзакции.

Публикация разрешена без готовых историй и даже для черновика без построенного пути; в последнем случае просмотр показывает «Маршрут ещё не построен», запуск недоступен. При сохранении публичного маршрута без геометрии публичный просмотр честно отражает это состояние. Удаление аккаунта каскадно удаляет прогулки и отзывает ссылки, но не удаляет общие аудиофайлы.

### 4. Общий проигрыватель и данные начальной прогулки

Создать `backend/walk-view.mjs` для адаптации существующих опубликованных форматов к `WalkView`; адаптер каталога вынести в `backend/walk-catalog.mjs`. При необходимости сделать декларации типов для клиента. Ни один адаптер не синтезирует доказательства, даты проверки или метаданные TTS, которых нет в исходном результате.

Кожевники преобразуются из `public/data/routes/paveletskaya.json` общим адаптером каталога; сохранить ID маршрута/глав, геометрию, тексты, источники, MP3 и текущие редакторские публикации. JSON и генератор `backend/builtin-routes.mjs` остаются источником начальных данных, не вторым движком прогулок. Не приписывать начальный маршрут случайному реальному пользователю. В списке он доступен как обычная карточка примера; пользователь может сделать собственную копию через общий документ и конструктор, исходные редакторские данные не изменяются.

Существующий редактор `backend/walk-admin.mjs` сохраняет редактирование и переозвучку начального контента. Изменить интеграцию чтения в `walk-catalog.mjs`, чтобы общий resolver видел действующую публикацию. Сохранить проверки совместимости старых глав; не делать массовую миграцию историй/редакторских заданий ради UI-рефактора.

Изменить `tour-experience.tsx`, `types.ts`, `walk-plan.tsx`, `walk-map.tsx`, `story-content.tsx`, `route-notes.tsx`, `use-playback-progress.ts`:

- `TourExperience({walk: WalkView, ...})` отображает любую прогулку, включая полностью неготовую, без зависимости от `pois[0]`. Загрузку данных и выбор маршрута выполняет внешний экран. Оболочку главной/регистрацию service worker отделить от проигрывателя.
- Показывать все остановки, даже без истории. Текст и аудио — независимые возможности: готовый текст можно читать при неудачной озвучке. Не воспроизводить тестовый сигнал как замену отсутствующей записи.
- Счётчики, заголовки, длительность, финиш, подписи источников и номера выводятся из данных. Использовать русское склонение числительных. Отсутствующая дата проверки не превращается в Invalid Date или сегодняшнюю дату.
- Ручные «Назад/Дальше» проходят по исходным остановкам. В режиме «Подряд» автоматически запускать соседнюю готовую запись; на неготовой/текстовой остановке остановиться и показать её статус с возможностью перейти дальше. Геотриггер не пропускает незаметно остановки и не начинает генерацию.
- Обновление завершённых историй можно применять между записями по стабильному ID; не менять играющий текст/аудио, не сдвигать текущую главу по индексу. Изменение состава/геометрии владельцем во время прослушивания предложить применить после завершения текущей сессии. При новом открытии загружается последняя версия.
- Прогресс привязан к прогулке, остановке и идентичности записи; замена аудио сбрасывает только смещение этой записи. Локальные/личные/публичные представления не должны случайно делить прогресс разных пользователей.

Переработать `route-map.tsx`: строить превью по geometry/остановкам через общий компонент; ссылку OSM центрировать по данным. Фиксированный SVG не нужен для других маршрутов. `scripts/build-map.mjs` и `scripts/generate-walk-audio.py` оставить утилитами подготовки конкретного исходного примера; они не должны вызываться при создании пользовательских прогулок. При сохранении их в build документировать назначение, без расширения этой задачи до общего генератора иллюстраций.

### 5. Раздел «Прогулка» и маршрутизация

Создать `src/features/walks/walk-library.tsx`, `walk-screen.tsx`, `walk-loader.ts`, `walks.css`; изменить `src/app/walk/page.tsx`, `src/app/page.tsx`, `navigation/app-navigation*`, `explore/around-screen.tsx`, `explore/nearby-stories.ts`, `account/account.tsx`.

Контракт URL для статического экспорта:

- `/` — существующая карта; внешний вид и основное назначение сохранить.
- `/walk` — библиотека: сверху «Собрать прогулку», ниже локальные, личные после входа и доступный начальный пример. Не создавать вторую одинаковую карточку после синхронизации локального документа.
- `/walk?new=1` — новый локальный документ в конструкторе; параметры address/lat/lon с карты предварительно выбирают старт, не запускают маршрутизатор или платную генерацию автоматически.
- `/walk?local=<uuid>` — локальная прогулка; `/walk?id=<uuid>` — личная; `/walk?catalog=<id>` — начальная запись; `/walk?share=<token>` — публичная. `edit=1` открывает конструктор только для локального документа/владельца. Не использовать непредсобранные `/walk/[id]`.
- Сохранить старые входы `/?tab=walk` и `/walk?resume=1` как клиентские переходы к библиотеке/мигрированному черновику. Старое `/walk?address=...` трактовать как создание от места. Конфликтующие параметры не должны открывать случайную прогулку.

Библиотека имеет состояния загрузки, пустого списка, ошибки с повтором, гостя и недоступного storage. Карточка открывает просмотр, редактирование — отдельное действие. В просмотре владельца доступны переименование/редактирование, сохранение, публикация/отзыв и копирование ссылки с обработкой отказа Clipboard API. Публичный посетитель не получает управляющих действий владельца.

Развязать `AroundScreen` и один `Route`: карта получает коллекцию доступных историй/ссылок на остановки через адаптер каталога и существующий API. Сохранить текущие точки примера и возможность слушать их с карты, передавая ID выбранной прогулки и главы. Не потерять существующие точки при удалении импорта из `page.tsx`; если для сохранения константы `MELNIKOV` требуется перенос, вынести её в данные начального каталога без нового исследования.

Убрать «Создать» из нижнего меню, корректно подсвечивать «Прогулка» во всех `/walk`-состояниях; создание отдельной истории `/create` остаётся доступным с карты/карточки дома. Адаптировать CSS островка к трём пунктам, сохранив центрирование и мобильную компоновку.

### 6. Загрузка, ошибки и офлайн

Изменить `published-route.ts`/`published-route-cache.ts`: сохранить legacy-слияние только для совместимости; новый loader валидирует целый `WalkView`, не требует встроенного base. Создать `src/features/walks/offline.ts` и общий ограниченный transport для новых операций; при переиспользовании `walk-builder/request.ts` обновить его тесты.

Правила запросов: общий дедлайн 20 секунд, AbortController при смене маршрута/размонтировании, максимум три попытки с задержками примерно 500/1000 мс и jitter, учитывать ограниченный Retry-After. Повторять только сеть, timeout, 429 и временные 5xx. Не повторять 400/401/403/404/409/ошибку схемы; повтор записи допустим только с сохранённым ключом идемпотентности или определённым восстановлением CAS. После исчерпания попыток — русское сообщение и ручной повтор. Poll статуса не должен создавать пересекающиеся запросы, работает только для активного просмотра и останавливается при терминальных состояниях.

Сохранить офлайн-доступ к примеру. Для пользовательских прогулок добавить явное «Сохранить для прогулки без сети»: сохранить проверенный manifest и доступные записи с проверкой размера/хеша, затем атомарно переключить указатель на комплект. Частично подготовленный маршрут можно сохранить с честным числом доступных историй; не утверждать готовность всех записей. При сбое не потерять предыдущий исправный комплект. Карта тайлов может требовать сеть; геометрия/список остановок и сохранённые истории доступны без неё.

Добавить `/walk` в `scripts/service-worker-manifest.mjs`, нормализацию `/walk.html` и `/walk/` в `public/sw.js`; query-параметры выбирают документ на клиенте. Не кешировать приватные `/api/me/*` в общем service worker. Приватные комплекты хранить отдельно по аккаунту, удалять/скрывать при выходе, не выдавать другому пользователю. Общие аудиофайлы не удалять без проверки ссылок остальных комплектов.

Для публичных ссылок сеть имеет приоритет: 404 после отзыва/удаления не заменять старым публичным ответом. При отсутствии сети явно обозначать сохранённую копию и её дату; уже скачанный файл нельзя дистанционно отозвать. Завершившиеся истории подгружаются при наличии сети, не обещать «последнюю редакцию» офлайн.

## Тестирование и проверка

1. Модель/миграция: ноль готовых историй, только текст, смешанная готовность, 1/2/5 остановок, отдельная история старта, loop без повторной главы, перестановка со стабильными ID, повреждённая геометрия, лишние поля, неизвестная версия. Миграция старого локального/server snapshot идемпотентна и сохраняет исходник при ошибке.
2. Хранение/API: две независимые прогулки одного пользователя; изоляция двух пользователей; CAS-конфликт; потерянный ответ создания и повтор; тот же ключ с иным payload; ограничения размера; restart после миграции. Полный happy path через реальную временную account/content SQLite и HTTP API.
3. Публикация: guest получает только shared; включение/выключение/удаление/удаление аккаунта; постоянный токен после изменения названия; сохранённая новая редакция сразу читается по ссылке; публикация до готовности и завершение истории без пересохранения. Проверять отсутствие recovery token, email, owner, служебных заданий и неутверждённых текстов в JSON. Открытие/публикация не расходуют квоту и не вызывают провайдера.
4. Проигрыватель: все остановки видны при частичной готовности; ручные и автоматические переходы; отсутствие тестового сигнала; текст без аудио; завершение/ошибка подготовки; смена маршрута останавливает старый звук и геолокацию; обновление записи не прерывает текущую; восстановление по ID/хешу после перестановки и замены аудио. Сохраняются проверки Media Session, Wake Lock и геотриггера.
5. Регрессия примера: четыре главы Кожевников, исходный порядок, источники и MP3; редакторская переозвучка появляется в общем просмотре; пользовательская копия не меняет оригинал. Второй маршрут другого района не показывает его карту, число глав, время или «историю на финише».
6. Офлайн: оболочка `/walk` с разными query, полный/частичный комплект, оборванное скачивание, неверный хеш, квота storage, Range-запрос аудио, обновление manifest, выход и вход другим пользователем, отзыв публичной ссылки онлайн. Не подменять 401/404 устаревшей копией.
7. Расширить существующие `navigation/app-navigation.test.ts`, `tour/published-route*.test.ts`, `tour/walk-plan.test.ts`, `walk-builder/model.test.ts`, `walk-builder/research.test.ts`, `lib/offline/*.test.ts`, `backend/walk-admin.test.mjs` по изменённым контрактам; не переписывать осмысленные проверки под новую реализацию только ради зелёного результата.
8. На поддерживаемом Node выполнить `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `node scripts/build-walk-catalog.mjs --check`. Перед каждым коммитом — lint/typecheck/test согласно правилам репозитория. Платные внешние API в тестах не вызывать.
9. Сквозная проверка production-сборки в браузере: карта → создание от места → локальное сохранение двух маршрутов → вход/сохранение → просмотр/редактирование → публичная ссылка в другой сессии → обновление/отзыв → офлайн-перезагрузка. Отдельно проверить мобильную навигацию, доступность с клавиатуры, отказ геолокации, воспроизведение готовых глав. Использовать временные данные и заранее подготовленные/mock истории; не запускать платную генерацию ради проверки. Если браузерная проверка недоступна, зафиксировать это явно, не объявлять её выполненной.
