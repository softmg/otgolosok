# План: исправить подтверждённые дефекты надёжности по код-ревью

Status: implemented 2026-09-21 in branch `feat/auth-account-osm-pipeline` (browser multi-tab and fresh offline-session checks were covered by deterministic unit/build verification; manual browser E2E was not run).

> Снимок на дату создания: факты ниже относятся к проверенному коду и могут устареть. Перед реализацией сверить их с текущей веткой; этот план не заменяет документацию архитектуры.

## Контекст

[Код-ревью](../project-code-review-2026-09-21.md) выявило шесть приоритетных дефектов в учёте генераций, сохранности аудио, офлайн-сборке и личном кабинете. Существующие 393 JS/TS-теста проходят и эти случаи не обнаруживают. Цель следующего этапа — устранить подтверждённые нарушения существующих контрактов, начиная с риска расходов и потери файлов.

Внешние платные API для реализации и тестов не нужны. Локальные стенды используют временные данные и подставные провайдеры; состояние production не изменяется.

## Согласованные решения

1. Пользователь сначала запросил ревью проекта и рекомендации, а затем явно поручил реализовать этот план.
2. Документы на русском согласно прямым инструкциям пользователя. Новые ветки, инфраструктура и интеграции не создаются.
3. Дальнейшие шаги — технические рекомендации по сохранению существующего поведения. Новые лимиты, способы входа, правила публикации и удаления пользовательских данных не предлагаются.

## Проверенные факты кодовой базы

- `backend/server.mjs:397–404` создаёт адресное задание независимо от результата `attachRequest()`. `backend/account-store.mjs:68–70` не связывает ключ идемпотентности с параметрами операции.
- Пользовательские квоты/история находятся в auth DB; задания — в jobs DB. Между записями в этих базах нет общей транзакции.
- `backend/audio-ingest.mjs:36–39` возвращает артефакт, уже перенесённый в общий `<sha256>.mp3`. `backend/server.mjs:145–149` удаляет общий путь при отказе текущей загрузки.
- `scripts/build-service-worker.mjs:5–8` применяет POSIX-регулярное выражение к платформенным путям. Windows-сборка содержит 7 assets без JS и аудио.
- `src/features/auth/login.tsx:10` проверяет текстовый префикс returnTo, а не origin разобранного URL.
- `src/features/account/account.tsx:15` реагирует на любое событие storage и не использует курсоры трёх списков.
- Next.js `16.3.4` использует статический export. Перед изменениями клиентского кода прочитать релевантные руководства установленного пакета в `node_modules/next/dist/docs/`.

## Реализация

### 0. Сначала зафиксировать воспроизведения

Дополнить `backend/account-api.test.mjs` интеграцией с настоящим account store и временными базами. В `backend/server.test.mjs` и `backend/audio-ingest.test.mjs` добавить сценарии сохранности существующего артефакта. Подтвердить падение тестов на текущем коде до исправления.

### 1. Связать идемпотентность с конкретной генерацией

Изменить `backend/account-store.mjs` и обработчики генерации в `backend/server.mjs`:

- Хранить тип операции, отпечаток нормализованных параметров и связанный job ID для ключа пользователя. Не принимать другой payload под тем же ключом: 409 до побочных эффектов.
- Повтор одинакового запроса возвращает исходный job ID и не расходует персональную/общую квоту повторно. Готовый общий результат сохраняет текущие условия бесплатного повторного использования.
- Сделать совместимую миграцию существующих записей. Не считать старые записи доказательством совпадения параметров, если эти параметры восстановить невозможно; в таком случае возвращать явный конфликт.
- Обработать сбой между резервированием, созданием задания и привязкой истории. Использовать устойчивое состояние операции с восстановлением по детерминированному ключу задания; не заявлять атомарность двух отдельных SQLite-баз.
- Проверить тот же контракт для POST исследования прогулки и возврата квоты при отказе. Менять схему и store исследования только при необходимости, сохраняя приватность recovery token.

Тесты: одинаковый запрос/ключ, разные адреса с одним ключом, разные операции с одним ключом, разные пользователи, седьмая генерация при лимите 6, готовый общий результат, ошибка создания и восстановление после промежуточного сбоя. Глобальный лимит в тесте персональной квоты должен быть выше персонального.

### 2. Сохранить общие аудиофайлы при отказе загрузки

Изменить `backend/audio-ingest.mjs`, `backend/server.mjs` и соответствующие тесты:

- Передать ожидаемый upload checksum в ingest и проверять его до переноса результата в общий каталог.
- Разделить подготовку временного MP3 и публикацию артефакта. Явно определить владение временными файлами и cleanup в `finally`.
- Ошибка checksum, истечение lease, отмена задания или ошибка записи receipt не должны удалять общий `<sha256>.mp3`.
- Не вводить удаление общих артефактов в обработчике отказа. Если меняется существующий `scripts/prune-audio.mjs`, сначала проверить все виды ссылок и гонки; самостоятельная переработка уборки не требуется для устранения удаления в HTTP-обработчике.
- Сохранить ограничения размера/длительности, нормализацию, контроль свободного места и идемпотентный receipt.

Тесты: успешная загрузка; неверный checksum; ранее существующий файл с тем же output hash; отказ accept после ingest; потеря lease; повтор успешной загрузки; временные файлы очищены, опубликованное аудио продолжает отвечать на GET/Range.

### 3. Исправить платформенные пути офлайн-сборки

Изменить `scripts/build-service-worker.mjs`. Нормализовать относительные пути в `/` до фильтрации и построения manifest; сохранить стабильный порядок и хеширование содержимого. При необходимости вынести чистую сборку manifest в `scripts/service-worker-manifest.mjs` и добавить `src/lib/offline/precache-manifest.test.ts`, чтобы тесты входили в существующий Vitest-запуск.

Проверить Windows- и POSIX-пути, наличие JS/CSS/шрифтов/карт/MP3, исключение админских страниц, корректность URL. Затем проверить настоящий `out/sw.js` после `pnpm build` и офлайн-запуск свежей браузерной сессии после первоначального кеширования. Старый кеш не должен маскировать дефект.

### 4. Ограничить переход после входа текущим origin

Создать `src/features/auth/return-to.ts` с чистой функцией `safeReturnTo(value: string | null, origin: string): string`, использовать её в `src/features/auth/login.tsx`. Разбирать URL с try/catch, проверять origin и схему; возвращать pathname/search/hash либо `/account`.

В `src/features/auth/return-to.test.ts` проверить внутренний путь с query/hash, пустое значение, `//host`, обратные слеши, управляющие символы и схемы внешних URL. Не ограничиваться тестом строкового префикса.

### 5. Исправить события выхода и пагинацию кабинета

Изменить `src/features/account/account.tsx`, при необходимости выделить обработку событий в `src/features/auth/session-events.ts` с тестами `session-events.test.ts`:

- Storage-событие выхода распознаётся по точному ключу, используемому `announceSignOut()` в `src/features/auth/client.ts`; BroadcastChannel — по значению `signed-out`.
- Изменение черновика или прогресса не перенаправляет пользователя и не сбрасывает ввод имени.
- Хранить отдельный cursor, состояние загрузки и ошибку для прогулок, запросов и избранного. Добавить «Показать ещё», объединять без дублей, сохранять существующие элементы при ошибке, разрешать повтор.

Проверить пустой список, 20 и 21 запись, все страницы без пропусков, двойное нажатие, повтор после сетевой ошибки и смену сессии. Браузерная проверка: две вкладки, ввод имени в кабинете, изменение черновика в конструкторе, настоящий выход из второй вкладки. Пока проект не имеет браузерного тестового запуска, выполнить этот сценарий вручную и записать результат; новую CI-инфраструктуру не добавлять автоматически.

## Тестирование и проверка

Использовать поддерживаемую Node.js `>=24.20.0` и pnpm `10.24.0`. На машине ревью установлена `24.18.0`, поэтому успешный локальный результат не заменяет прогон на заявленной версии.

Перед каждым атомарным коммитом выполнить `pnpm lint`, `pnpm typecheck`, `pnpm test`. Для итоговой проверки выполнить также `python scripts/test-import-osm-attractions.py`, `pnpm build`, проверку содержимого manifest и перечисленные HTTP/браузерные сценарии. Не обращаться к платным API из тестов. Изменения протокола загрузки аудио проверить существующими worker-тестами и HTTP-запросами с реальным FFmpeg на небольшом локальном WAV.

Каждое исправление сопровождать регрессионным тестом и отдельным Conventional Commit с русским описанием. Сохранить результаты и ограничения в заметке ревью; не объявлять E2E пройденным по одному результату unit-тестов.

## Фактическая реализация

- `backend/account-store.mjs` хранит намерения генерации по пользователю и ключу вместе с операцией, отпечатком запроса и job ID. Повторы одинакового запроса возвращают исходное задание; несовпадающие и устаревшие ключи получают 409. Отдельные SQLite-базы не объявляются атомарными: завершённое намерение позволяет восстановить ответ после его потери, а незавершённое намерение освобождается при ошибке создания.
- `backend/audio-ingest.mjs` проверяет checksum входной загрузки до FFmpeg и публикации. HTTP-обработчик больше не удаляет общий артефакт при отказе текущего задания.
- Генератор service worker использует нормализованные `/` пути и чистые функции manifest. Windows production build создал manifest из 55 файлов вместо 7.
- Вход проверяет разобранный origin `returnTo`, а кабинет различает явное событие выхода и обычные изменения localStorage. Три серверных списка получили независимую курсорную пагинацию с повтором после ошибки и устранением дублей.
- Ручные браузерные проверки двух вкладок и свежей офлайн-сессии не запускались: в репозитории нет браузерного раннера. Их критические правила зафиксированы чистыми unit-тестами; настоящий build manifest проверен сборкой.
