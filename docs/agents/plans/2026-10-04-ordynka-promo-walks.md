## Проверенные факты проекта

- `backend/promo-walks.mjs`: служебный владелец `PROMO_WALKS_USER_ID = "promo-walks"`; `createPromoWalkService` планирует, создаёт документ и открывает его через `setWalkVisibility(..., "public", {autoApprove: true})`. Повтор защищён `idempotencyKey`.
- `backend/walk-document.mjs`: документ версии 2 хранит `storyRef`, отдельный `triggerLocation`, маршрут и `fieldChecked`; допустимые значения `minutes` — 15, 30, 60 и 90. Расчёт общей длительности нельзя записывать как измеренную длительность аудио.
- `backend/walks.mjs`: штатный `createWalkPlanner` используется редакционными пакетами для пешеходного пути; формат изучен в `artifacts/boulevard-chistye/plan.mjs`.
- `content/boulevard-chistye-kitay-2026-10-04/` содержит образец `stops.json`, `stories.json`, `walk.json`, лицензированных превью и квитанций озвучки.
- `backend/content-store.mjs`: `listPlaces` принимает максимум 100 записей на страницу. Для полного сопоставления использовать `hasMore` и `offset`; публичный сервер по умолчанию показывает только готовые рассказы, поэтому для инвентаризации нужен `status=all`.
- Публичный каталог 4 октября подтвердил три готовые карточки: галерея `osm:relation:1907261` — 118 слов; Инженерный корпус `osm:way:53548436` — 104; храм в Толмачах `osm:way:53548437` — 96. Фонтан `osm:node:1378700996` и памятник Шмелёву `osm:node:8044478986` существуют без текста.
- Дом писателей `osm:way:52435403` есть в `backend/walk-discovery-catalog.json`, но отсутствует в полученной выборке production. Геометрия из discovery — кандидат для сопоставления, а не подтверждение исторических фактов или доступного прохода.
- Для главного дома усадьбы Демидовых установлен `osm:relation:20429251`, Большой Толмачёвский, 3с5, по геометрии и расположенной внутри точке библиотеки. Не подменять её соседним домом Лобковой `osm:relation:20429256` по адресу Большой Толмачёвский, 5с7.
- Прежние купленные тексты и операционные снимки хранятся в игнорируемом `artifacts/`; в коммит идут собственные тексты, источники и сопоставления. Пример проверки импорта — `artifacts/boulevard-trubnaya/verify.mjs`.

Номера — направления исследования, а не обещание включить каждую главу. Повторяющиеся места используют одну утверждённую редакцию; каждый маршрут получает собственную последовательность и переходы. Не превращать серию в пять перестановок одинаковых остановок. Короткие адресные справки не растягивать искусственно.

## Реализация

0. **Подготовка серии.** Сохранить этот план, публичный список глав, исследование и рабочие остановки первой прогулки. Отмечать прочитанными только фактически открытые главы; сейчас это 4–18. Текущий этап не меняет production.
1. **Купленный источник.** Получить авторизованный доступ в рабочем браузере и прочитать главы-кандидаты первой прогулки; полные исходники хранить только в `artifacts/ordynka/`. Уточнить тематические границы остальных четырёх маршрутов по оставшимся главам. Результат сопоставления сохранить в `content/ordynka-tretyakovka-2026-10-04/stops.json`.
2. **Объекты и рассказы.** Для каждой остановки проверить название, адрес, сохранившийся объект, публичный ID и точку обзора. Запросить существующие тексты, сохранять редакторские черновики и версии. Создать самостоятельные рассказы в `stories.json`, обычно 180–250 слов при достаточных фактах; каждому абзацу дать ссылки на проверяемые факты и открытые источники. Не добавлять имя известного человека без доказанной связи с конкретным местом.
3. **Маршрут.** Через `createWalkPlanner` построить реальный пешеходный путь, сохранить валидный `walk.json`. Точки прослушивания ставить снаружи доступных фасадов; вход во дворы и музеи не делать обязательным. Проверить непрерывность, отсутствие лишних кругов и отклонения от остановок. `fieldChecked: false` до проверки на месте. Вычислить время ходьбы отдельно от оценочной длительности рассказов.
4. **Локальная проверка.** Загрузить пакет в изолированный `createStore`, разрешить все остановки через `resolveWalkView`, проверить документ через `validateWalkDocument`. Проверить пробный импорт с откатом, повтор без новых редакций и конфликт ожидаемых версий. Подготовить пакет к рассмотрению и записать состояние в `docs/agents/ordynka-promo-walks.md`.
5. **Публикация и звук.** Когда объём готового пакета и дальнейший выпуск определены пользователем, применить штатный процесс с резервной копией затронутых записей, проверками версий и идемпотентностью. Создать промопрогулку от служебного аккаунта, сверить публичный API и каталог. Для озвучки использовать принятый профиль промопрогулок только после определения этого этапа; проверять текущую редакцию текста, хеши и фактическую длительность каждого MP3. Выбор лицензированных фото и подготовку ролика выполнять отдельным этапом.
6. **Остальная серия.** Пройти шаги 1–5 для маршрутов 2–5; после каждого обновлять таблицу и фактические главы. План всей серии закрыть только после завершения всех согласованных этапов, не после одного маршрута.

Сетевые запросы ограничивать таймаутом и числом повторов; 429, 5xx и временные ошибки повторять с ограниченным экспоненциальным ожиданием. Ошибки авторизации, неверные параметры и закрытый платный доступ не обходить повторными запросами.

## Проверки

- Для текущего документального этапа: 97 уникальных глав с последовательными номерами; все ссылки остановок ведут на существующие главы; ID совпадают с публичным каталогом или явно помечены кандидатами. Проверить все ссылки на локальные файлы и отсутствие платных текстов в коммите.
- Перед каждым коммитом выполнить `pnpm check` по правилам репозитория. Новые тесты приложения не нужны для плана и редакционного исследования.
- Для готового пакета: проверить связи абзац → факт → источник, уникальность остановок, валидный документ и разрешение всех рассказов в изолированной базе. Тесты не вызывают платные API.
- Для выпуска: открытие публичной ссылки в мобильном браузере, все остановки, переходы, источники и карта; после озвучки отдельно воспроизведение и пауза, соответствие аудио текущей редакции.
