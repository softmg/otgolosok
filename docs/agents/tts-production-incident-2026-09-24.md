# Почему production показывает «Remote TTS delivery failed», 24 сентября 2026 года

Диагностика выполнена только чтением баз и состояния серверов. Production не менялся.

## Ошибка 42 аудиозаданий

В базе сайта `external_audio_jobs` находятся 42 завершённых ошибкой задания F5. Все имеют `error_json.code = AUDIO_DURATION`, по три попытки. Задания созданы 22 сентября около 19:31 МСК; последняя неудачная попытка завершилась около 00:27 МСК 23 сентября. Общее сообщение `Remote TTS delivery failed` записывает HTTP-диспетчер при разных сбоях, поэтому причину нужно читать из `error_json.code`.

Все 42 исходных текста имеют `effectiveProfile: description-v1` и `audioDisposition: not_applicable_short_text`. Их длина в поле `spokenText` — от 21 до 54 слов, медиана 39. Массовая постановка озвучки `enqueueMissingPlaceAudio()` выбирает любой утверждённый текст без аудио и не проверяет `audioDisposition`. Поэтому короткие описания ошибочно отправились в F5. Обычная автоматическая постановка озвучки и утверждение редактором эту пометку проверяют.

TTS-сервер успешно синтезировал и сохранил результат для каждой из 126 попыток. В его базе длительность всех этих результатов — 12,84–29,904 секунды; все меньше 30 секунд. В каждом задании сайта сохранены ограничения F5: `minimumPublicationDurationSec: 30`, `maximumPublicationDurationSec: 150`. Техническая проверка MP3 допускает до 600 секунд, но при принятии результата проверяется предел публикации. После скачивания файла сайт отклонил его с `AUDIO_DURATION`. Повтор каждой попытки не менял текст и предсказуемо дал ту же длительность. На TTS-сервере результаты этих попыток истекли по сроку хранения; в базе сохранились метаданные, аудиофайлы не публиковались.

На момент диагностики правило `not_applicable_short_text` исключало короткие описания из автоматической озвучки. Массовая команда всё равно включала их в очередь; до изменения нижнего порога повторение 42 заданий было бы бессмысленным.

По решению пользователя нижний порог публикации удалён из backend. Новые профили больше не содержат `minimumPublicationDurationSec`; при приёме результата поле старых заданий игнорируется. Положительная конечная длительность, верхняя граница публикации 150 секунд, проверка MP3 и технический предел 600 секунд сохраняются. После выкладки кода и восстановления GPU старые задания можно повторить без изменения текста. Массовая команда по-прежнему озвучивает утверждённые короткие описания, когда редактор запускает её вручную; автоматическая постановка следует `audioDisposition`.

## Отдельная текущая неисправность GPU

Последняя успешная аудиопубликация сайта была 23 сентября в 03:57 МСК. После неё на TTS-хосте в журнале `systemd` зафиксированы reload в 16:53 и 16:56 МСК. На момент проверки 24 сентября GPU виден хосту, но в контейнере `just-tts-private-tts-1` `nvidia-smi` выдаёт `Failed to initialize NVML: Unknown Error`, а `/usr/bin/python3.12` сообщает `torch.cuda.is_available() == False` и ноль устройств. Контейнер при этом помечен healthy: его healthcheck не проверяет CUDA. Новых заданий после последней успешной публикации нет, поэтому эта неисправность не объясняет указанные 42 ошибки `AUDIO_DURATION`, но следующий синтез F5 сейчас неработоспособен. Сходство с инцидентом 22 сентября и время reload указывают на повторную потерю доступа к GPU; точный момент отзыва доступа не записан.

Для восстановления нужно сначала пересоздать только TTS-контейнер после проверки отсутствия активных заданий и резервной копии SQLite, затем проверить CUDA из контейнера и короткий синтез из production backend. Долгосрочно следует устранить потерю GPU при reload переходом на поддерживаемое подключение устройств и сделать readiness зависимым от состояния CUDA и исполнителя. Это отдельная инфраструктурная работа на общем GPU-хосте.

## Восстановление и переход на CDI, 15:34–15:40 МСК

Перед первым пересозданием на TTS-хосте проверено отсутствие `queued` и `running`: 1025 заданий были подтверждены, 127 истекли, 35 завершились ошибкой. Создана согласованная SQLite-копия `/var/backups/just-tts/20260924T123444Z-gpu-recovery.sqlite` с правами `0600`, `PRAGMA integrity_check` вернула `ok`. Пересоздан только сервис `tts`, после чего `nvidia-smi` и PyTorch внутри контейнера увидели GPU; выделение CUDA-тензора прошло. Диагностическое задание из production backend `8d772721-3d63-445b-97d5-6a4052ff07b3` вернуло MP3 размером 31 917 байт: SHA-256 совпал, FFmpeg полностью декодировал файл, результат подтверждён через `ack` и не опубликован на сайте.

На хосте Docker 25.0.2, NVIDIA Container Toolkit 1.19.0 и `runc` 1.1.12. [NVIDIA описывает](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/troubleshooting.html#containers-losing-access-to-gpus-with-error-failed-to-initialize-nvml-unknown-error), что legacy NVIDIA hook может терять доступ к GPU при `systemd daemon-reload`, и рекомендует CDI как один из способов устранения. Команда `nvidia-ctk cdi generate` создала постоянную спецификацию `/etc/cdi/nvidia.yaml`; отдельный пробный контейнер успешно получил GPU через `--runtime=nvidia` и `NVIDIA_VISIBLE_DEVICES=nvidia.com/gpu=all`. Прямое `docker run --device nvidia.com/gpu=all` на установленном Docker 25 не заработало: CDI-функция daemon здесь не включена. Поэтому для TTS выбран поддерживаемый NVIDIA runtime в режиме CDI без перезапуска общего Docker daemon.

После завершения появившегося во время работ рабочего задания проверено, что очередь снова пуста. В `just-tts-private` коммит `8298a81` заменил legacy GPU reservation на CDI и дополнил Docker healthcheck проверкой `nvidia-smi` вместе с `/readyz`. Только TTS-контейнер пересоздан с новой конфигурацией: `runtime=nvidia`, `device_requests=0`, PyTorch выделил CUDA-тензор. Повторное диагностическое задание из production backend `2940275e-a1c3-48d3-baf7-71463f12ac2d` вернуло MP3 размером 31 917 байт; хеш и декодирование прошли, результат подтверждён через `ack`. `docker compose config --quiet`, `ruff check just_tts tests` и 22 Python-теста прошли. `pyright just_tts tests` по-прежнему выдаёт шесть ошибок в ранее существовавших `jobs.py` и `test_jobs.py`, не затронутых изменением Compose.

На общем GPU-хосте есть другие контейнеры с legacy GPU reservation. `systemctl daemon-reload` специально не выполнялся, чтобы не отозвать их доступ к GPU. Штатный `nvidia-cdi-refresh.service` на этом хосте пропускает запуск по `ExecCondition`; он оставлен выключенным. Спецификация в `/etc/cdi` переживает перезагрузку, но **после обновления драйвера или состава GPU её нужно пересоздать** командой `nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml` и проверить доступность GPU в новом TTS-контейнере. Надёжное автоматическое обновление спецификации требует отдельной настройки systemd без затрагивания остальных legacy GPU-контейнеров. `/readyz` самого API по-прежнему не проверяет состояние исполнителя; новый Docker healthcheck проверяет GPU, но не устраняет эту отдельную слепую зону.

## Восстановление 24 сентября

Перед перезапуском на TTS-сервере не было `queued` или `running` заданий. Согласованная SQLite-копия с `quick_check = ok` сохранена с правами `0600` в `/var/backups/just-tts/20260924T123531Z/api.sqlite`. Пересоздан только сервис `tts` через штатный Compose без пересборки образа и без удаления тома. После запуска `nvidia-smi` внутри контейнера и PyTorch снова увидели одно CUDA-устройство.

Production backend обновлён штатным скриптом с резервной копией `backups/generator-20260924T123628Z/generator.tar.gz`; после запуска он healthy и загружает профиль F5 без `minimumPublicationDurationSec`. Из работающего backend выполнен короткий диагностический синтез `32047ba6-686d-45ec-923a-d098dc23d64f`: MP3 длиной 5,28 секунды получен, SHA-256 совпал, результат подтверждён через ack и удалён с TTS-сервера без публикации на сайте. Одно прежнее задание `7b0fb638-bece-4fb4-8894-6c80e41ba405` повторено и успешно опубликовано с длительностью 27,744 секунды.

Остальные 41 задание повторены после проверки неизменности утверждённого текста и отсутствия готового аудио. Сразу после постановки несколько обращений получили временный `TTS_API_FAILED`; штатные повторы восстановились без вмешательства. К 15:59 МСК все 42 задания завершились `succeeded`, аудио прикреплено ко всем 42 текстам; длительность MP3 — 12,84–29,904 секунды. Публичный range-запрос к одному из восстановленных файлов вернул HTTP 206, `audio/mpeg`, 1024 байта. На TTS-сервере нет `queued/running`, CUDA доступна. Риск повторной потери GPU после `systemd reload` остаётся до инфраструктурного исправления и корректного readiness.
