# Адресные ориентиры из OSM

`scripts/build-osm-address-index.py` собирает SQLite-индекс всех адресных объектов, именованных улиц и административных районов из PBF Москвы. Отбор по исторической значимости не применяется. Контуры зданий сохраняются с внутренними дворами и частями мультиполигонов, неполная геометрия пропускается и учитывается в отчёте. Новый файл заменяет прежний только после успешного импорта и проверки целостности.

```sh
uv venv --python 3.12 /tmp/otgolosok-osm
uv pip install --python /tmp/otgolosok-osm/bin/python osmium==4.3.1
/tmp/otgolosok-osm/bin/python scripts/build-osm-address-index.py /path/to/Moscow.osm.pbf \
  --output backend/data/osm-addresses.sqlite
/tmp/otgolosok-osm/bin/python scripts/test-build-osm-address-index.py
```

Python и osmium нужны только при сборке. Backend открывает `${DATA_DIR}/osm-addresses.sqlite` для чтения при запуске; новый индекс нужно загрузить атомарно и перезапустить генератор. При отсутствии файла сохраняется прежний поиск по небольшому каталогу достопримечательностей. Повреждённый или несовместимый файл приводит к явной ошибке запуска; ошибка чтения во время задания останавливает попытку до платного поиска и показывается как `OSM_ADDRESS_LOOKUP_FAILED`.

`backend/osm-geocoder.mjs` выбирает кандидатов через R-tree в радиусе 300 м. Расстояние считается до геометрии, а не центра здания. Точка внутри внешнего контура, но во внутреннем дворе, не считается расположенной в здании; попадание на границу отмечается отдельно. Для административного района выбирается наименьший подходящий контур. Для объектов-полигонов вывод относится только к сохранённой репрезентативной координате, а не ко всей площади объекта.

Результат сохраняется в `content_jobs.checkpoint_json.locationContext`: исходные координаты, версия формата, источник и SHA-256 снимка, здание вокруг точки, два ближайших различных адреса, улица, район и расстояния. Это геометрические ориентиры, а не подтверждённый почтовый адрес или доказательство исторических утверждений. Поле `places.address` не изменяется. Исследователь и проверяющий получают один контекст и явный запрет переносить адрес или историю соседнего здания на объект. Отказ проверки идентичности по-прежнему останавливает генерацию.

Обычный повтор сохраняет контекст вместе с найденными источниками; повтор с `restartFrom: "research"` удаляет прежнюю контрольную точку и выполняет геопоиск и исследование заново. Обновление индекса само по себе не перегенерирует опубликованные тексты.

## Снимок и предварительная проверка 22 сентября 2026 года

Использован тот же PBF, что у production Valhalla: SHA-256 `86b5684276bc35a231cd3afba53647cd261731eccba34bdf89f9d553ba2a91b5`, последнее редактирование включённых объектов — 4 сентября 2026 года. Индекс занимает около 76 МиБ: 121 392 адресных здания, 13 065 адресных объектов, 41 530 участков именованных улиц и 111 административных контуров. Пропущена одна неполная геометрия. Источник: [BBBike Moscow](https://download.bbbike.org/osm/bbbike/Moscow/), лицензия ODbL-1.0, © OpenStreetMap contributors.

На выгрузке 342 заданий с `ADDRESS_UNCLEAR` у 150 отсутствовал собственный адрес. Индекс дал ориентиры для 146 из них: 26 попаданий координаты в адресное здание, 140 точек с соседними адресами, 142 с ближайшей улицей, 145 с районом (группы пересекаются). Старый каталог давал соседние адреса только для 110 из этих 150. Это измерение покрытия, а не доли исправленных текстов.

Для пилота отобраны 25 точек без собственного адреса: десять с попаданием в здание, десять с соседними адресами и пять с улицей/районом без адресного здания рядом. В выборке, например, Art4 получил контур здания «Хлыновский тупик, 4», музей Игоря Талькова — «Черниговский переулок, 9/13 с3», памятник Хачатуряну — адресные ориентиры в Брюсовом переулке. Это результаты OSM, требующие проверки источниками; ни одному объекту адрес автоматически не присвоен.

## Развёртывание и запуск пилота

22 сентября 2026 года развёрнут backend ревизии `828b4e7` через штатный `deploy-otgolosok-generator` из отдельной копии коммита. Перед остановкой партия временно поставлена на паузу, активное задание завершилось само. После обновления партия возвращена в `running`; Valhalla и фронтенд не пересоздавались.

Резервная копия генератора: `backups/generator-20260922T155125Z/generator.tar.gz`. Согласованный снимок базы до пилота, исходные состояния, список 25 точек и результаты операций находятся в контейнере в `/data/ops-backups/geocoding-pilot-2026-09-22T155011878Z/` (каталог 0700, файлы 0600). `manifest.json` содержит координаты и рассчитанные ориентиры, `started.json` — список повторно запущенных заданий, `priorities.json` — исходные приоритеты.

Все 25 заданий повторены через `retryBatchItem(..., {restartFrom: "research"})`, старые исследовательские контрольные точки очищены. Только этим заданиям временно назначен приоритет 1000, чтобы пилот прошёл перед остальной очередью; число одновременных задач осталось равным 1. После окончания пилота исходные приоритеты восстановлены из сохранённого файла; подтверждение операции — `priorities-restored.json`. Для просмотра хода проверки нужно сопоставить `jobId` из `started.json` с `content_jobs`: состояние, `error_json`, `checkpoint_json.locationContext` и `checkpoint_json.evidence`. `latest.json` — снимок последней ручной проверки, а не автоматически обновляемый мониторинг.

Проверены ESLint, TypeScript, 308 frontend-тестов, 287 backend-тестов, четыре Python-теста, Ruff и Pyright. На сервере поддерживается SQLite R-tree; контрольные суммы модулей геопоиска, контекста и генерации совпали с коммитом. `/api/story-service`, `/api/content/places?limit=1` и `/admin?section=content` вернули 200; административный API без входа вернул 401. Генератор и Valhalla здоровы. Первое живое задание сохранило `locationContext.status = "matched"`. Пилот завершился с 14 заданиями в `ready` и 11 в `review_required`; из последних десять получили `ADDRESS_UNCLEAR`, одно — общий `REVIEW_REQUIRED`. Во всех 25 заданиях геоконтекст был найден, но его наличие само по себе не заменяет редакторскую проверку.
