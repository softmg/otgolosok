# Восстановление каталога после обновления сервиса

## Поведение и регрессии

Каталог различает обычный сбой и HTTP 503 с кодом `SERVICE_MAINTENANCE`. Ошибка 503 представлена базовым `RequestError`, а не `RejectedRequest`: последний используется для HTTP 4xx. Проверка режима обновления покрыта таблицей положительного и отрицательных случаев.

При обновлении уже загруженные места остаются на карте. Вместо ручного повтора и прогресса показывается сообщение «Сервис обновляется. Карта загрузится автоматически». Загрузчики области карты и поиска рядом повторяют незавершённую загрузку каждые пять секунд; это работает и тогда, когда `/service-status` уже отвечает, а API каталога ещё возвращает режим обновления. Полностью загруженные области остаются в кеше.

Проверка `/service-status` выполняется при видимом документе, имеет тайм-аут и отменяется при размонтировании. Временная ошибка проверки сохраняет последнее известное состояние сервиса. Компонентные моки отдельно обрабатывают этот путь, чтобы запрос статуса не попадал в отложенные ответы каталога.

Браузерный сценарий восстановления сначала дожидается отказа каталога, затем переключает сервис в рабочее состояние и ждёт успешного ответа `/service-status`. Появление маркера само по себе не доказывает, что очередная проверка состояния уже завершилась: до неё сообщение об обновлении может оставаться видимым.

## Локальная проверка 1 октября 2026 года

- Полный `pnpm check` завершился успешно: ESLint, Stylelint, Prettier, обе проверки TypeScript, 596 frontend-тестов, 529 backend-тестов, Ruff, Pyright, 20 Python-тестов и 15 subtests, production-сборка.
- Первый широкий Chromium-прогон `interface.spec.ts` и `map-catalog.spec.ts`: 60 успешных сценариев, один сбой ожидания сообщения «Не все места загрузились.» после отказа второй страницы. На момент тайм-аута пяти секунд 100 мест сохранялись, статус оставался «Загружаем места: 100 из 101…».
- Без изменения кода этот сценарий прошёл три повторения; следующий широкий прогон завершился успешно — 61 из 61 сценария. Новый сценарий автоматического восстановления также прошёл в обоих широких прогонах.

Причина единичного тайм-аута не установлена. Первый широкий прогон выполнялся одновременно с production-сборкой в том же каталоге; влияние этого фактора не доказано. Сборку и браузерный dev-сервер следует проверять последовательно, чтобы исключить конкуренцию за генерируемые файлы. Если сбой повторится в последовательном прогоне, нужно зафиксировать время трёх попыток HTTP-запроса и переходов загрузчика, а не скрывать проблему произвольной задержкой или ослаблением assertions.

Production-деплой в рамках этой проверки не выполнялся.
