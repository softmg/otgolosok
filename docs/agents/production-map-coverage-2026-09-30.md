# Полнота точек на production-карте

Проверено 30 сентября 2026 года на https://otgolosok.online/. Проверка production выполнялась только чтением: SQLite открыт с `readOnly: true`, публичные запросы — GET, браузер — новая гостевая сессия без геолокации. Код приложения и production-данные не менялись.

## Результат

- В production-базе 1 460 неархивных мест с утверждённым текстом. У 1 438 есть аудио, у 22 — только текст; число 1 438 соответствует озвученным местам.
- Публичный `/api/content/places?limit=100&offset=…&status=ready` постранично возвращает все 1 460 уникальных мест, включая 1 438 с аудио. У всех записей числовые координаты.
- При открытии главной страницы браузер делает единственный запрос `/api/content/places?limit=100&status=ready`. Ответ: `total: 1460`, `places.length: 100`, `hasMore: true`; аудио есть у 99 записей этой страницы.
- В DOM карты 105 маркеров: 100 записей каталога, четыре главы встроенной прогулки и Дом Мельникова. Ошибок JavaScript при этой проверке не было.

## Причина и исправление

`src/features/explore/around-screen.tsx` запрашивает одну страницу с `limit=100`, сохраняет только `value.places` и не обрабатывает `hasMore` и `offset`. Поэтому 1 360 утверждённых записей каталога не попадают в начальный набор маркеров. При выборе центра радиус ограничивается 5 км, но предел в 100 записей остаётся. Перемещение и масштабирование карты сами по себе не запускают догрузку каталога.

Простое увеличение `limit` на клиенте не исправляет проблему: сервер допускает максимум 100 записей на страницу. Во время первоначальной проверки исправление не выполнялось; последующая правка описана ниже.

## Проверки перед сохранением заметки

ESLint прошёл; отдельный `pnpm test` завершился успешно: 404 frontend-теста и 489 backend-тестов. Общий `pnpm check` остановился на TypeScript: параллельно добавляемый `src/features/explore/place-photo.tsx` импортировал ещё отсутствующий `content/place-images.json`. Эти изменения не относятся к проверке карты и не включены в коммит заметки; полный цикл проверки и сборки поэтому не подтверждён.

## Исправление клиента

После поручения исправить дефект добавлены `published-catalog.ts` и `use-published-catalog.ts`. Клиент последовательно читает все страницы, добавляет маркеры по мере получения и объединяет записи по идентификатору. Неполная или противоречивая выдача не считается успешной загрузкой. Выбор центра и геолокация больше не сокращают каталог: рекомендации рядом фильтруются локально по существующим правилам расстояния.

Используется существующий транспорт запросов: до трёх попыток при сетевом сбое, таймауте, HTTP 429 и 5xx, с ограниченной экспоненциальной задержкой. При размонтировании запросы отменяются, поздние ответы не обновляют карту. Интерфейс показывает ход загрузки; при ошибке сохраняет полученные точки и предлагает повторить загрузку.

Регрессионный компонентный тест до исправления воспроизвёл 100 маркеров вместо 205. После исправления прошли 20 новых unit/компонентных сценариев, включая 1 438 записей, пустую выдачу, точную границу страницы, повторы, отмену, частичный отказ и геолокацию. Полный `pnpm check` прошёл: 435 frontend-тестов, 489 backend-тестов, Ruff, Pyright, 19 Python-тестов и 12 subtests, production-сборка.

Браузерные проверки: два новых сценария карты и семь сценариев фотографий прошли. Из 52 общих сценариев интерфейса 51 прошёл сразу; один обнаружил гонку проверки CSS scroll-анимации. Проверка переведена на `expect.poll`, после чего этот сценарий прошёл пять раз подряд; поведение приложения не менялось. Фикстуры каталога дополнены реальными полями API `total` и `hasMore`.

Собранный локальный frontend дополнительно проверен в Chromium с живыми ответами production API, полученными только GET-запросами через HTTP/2. На момент этой проверки в каталоге уже 1 461 место: все получены за 15 страниц, включая 1 438 с аудио. В DOM 1 466 маркеров с учётом пяти встроенных; каждому месту соответствует маркер, пропусков и ошибок JavaScript нет. Эта проверка не является выкладкой: production frontend в рамках правки не заменялся.
